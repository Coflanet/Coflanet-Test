# 태스크 분해 & 분리·병렬화 판단

PM이 작업을 섹션으로 나눌 때 쓰는 기준입니다.

## 분리·병렬화 결정 트리

1. **하위 작업들이 서로 독립적인가?**
   - 한 작업의 출력이 다른 작업의 입력이어야 한다면 → 의존 관계. 병렬화하지 말고 순서대로,
     또는 의존 사슬을 한 에이전트에 묶어라.
   - 서로 독립이면 → 병렬 후보.

2. **폭(breadth)이 넓은가?**
   - 여러 독립 방향을 동시에 파야 하면(예: 후보 20곳 각각 조사) → 강력한 병렬화 대상.
   - 깊이(depth) 한 주제를 끝까지 파는 거라면 → 보통 단일 에이전트가 낫다.

3. **정보량이 단일 컨텍스트를 넘는가?**
   - 넘으면 → 분리해서 각자 컨텍스트로 압축.
   - 작으면 → 굳이 나누지 마라.

4. **가치가 비용(≈15배 토큰)을 정당화하는가?**
   - 아니면 → 단일 에이전트.

위 넷 중 "독립 + (폭 넓음 또는 컨텍스트 초과) + 가치 충분"이면 오케스트라가 적합합니다.

## 섹션으로 나누는 방법

- **산출물 기준으로 자른다.** Conway's Law: 분업 구조가 곧 결과물 구조가 됩니다. 최종 산출물이
  "시장조사 / 경쟁사 분석 / 재무모델 / 요약문서"라면 섹션도 그대로 4개로.
- **상호 배타(MECE)에 가깝게.** 섹션 간 겹침은 중복 작업을, 빈틈은 누락을 낳습니다. 경계를 한 문장으로
  적을 수 없으면 아직 덜 쪼개진 것입니다.
- **노력을 복잡도에 맞춰 스케일링.** 단순=1명/3~10호출, 비교=2~4명/각 10~15, 복합=10+명.
- **계층은 필요할 때만.** 섹션 자체가 다시 여러 병렬 하위작업으로 갈라질 만큼 크면 그 섹션에 PL을 두고,
  아니면 PM이 플레이어에게 직접 위임(PL 생략).

## 분해 안티패턴 (Anthropic 사례 기반)

- **모호한 위임** — "반도체 공급난 조사해" → 서브에이전트마다 같은 검색을 하거나 엉뚱한 시기를 팜.
  반드시 목표·출력형식·도구·경계를 명시.
- **과분할** — 단순 질의에 서브에이전트 50개 생성. 노력 예산으로 상한을 둘 것.
- **의존 작업의 강제 병렬화** — 코딩처럼 단계 의존이 강한 작업을 억지로 쪼개면 조율 비용이 이득을 넘음.
- **중복 탐색** — 경계가 겹쳐 여러 에이전트가 동일 작업. MECE로 방지.

## 위임 명세 4요소 (모든 섹션에 필수)

각 위임에는 반드시 포함:

1. **목표(objective)** — 이 에이전트가 답해야 할 단 하나의 질문/만들어야 할 산출물.
2. **출력 형식(output format)** — 보고 형태(예: "표 3열: 회사·이사·출처 URL").
3. **도구·소스 가이드** — 어떤 도구/소스를 쓰고 무엇을 피할지(예: "1차 자료 우선, 콘텐츠팜 회피").
4. **경계(boundaries)** — 범위 안/밖. 다른 섹션과의 분담선을 명시("2025년만, 과거 사례 제외").
