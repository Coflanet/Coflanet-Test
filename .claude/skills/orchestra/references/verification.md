# 검증 라운드 · 평가 · 중단 · 실패 처리

종합 전에 결과의 품질을 확인하는 방법입니다. 핵심 직관: **실행자와 평가자를 분리**하면 신뢰성이 오릅니다
(Reflexion의 Actor/Evaluator 분리, Anthropic의 evaluator-optimizer 패턴).

## 검증 루브릭 (LLM-as-judge)

산출물이 free-form이라 정답이 하나가 아닐 때, 평가자 에이전트가 다음 기준으로 0.0~1.0 점수 + pass/fail를
매깁니다 (Anthropic 리서치 시스템 루브릭):

- **사실 정확성** — 주장이 소스와 일치하는가?
- **인용 정확성** — 인용된 소스가 실제로 그 주장을 뒷받침하는가?
- **완전성** — 요구된 모든 측면을 다뤘는가?
- **소스 품질** — 1차/권위 있는 소스를 썼는가, 콘텐츠팜에 의존했는가?
- **도구 효율** — 적절한 도구를 합리적 횟수로 썼는가?

실무 팁: 평가자를 여러 개로 쪼개기보다, **단일 평가 프롬프트가 점수를 내는 방식**이 더 일관적인 경우가
많습니다. 정답이 분명한 케이스는 평가자에게 "정답 맞췄는지"만 물으면 됩니다.

## 검증 방식 선택

- **단일 critic 검증** — 빠르고 저렴. 대부분의 섹션 1차 검증에 충분.
- **다중 critic (multi-agent critique)** — 서로 다른 관점의 평가자가 독립 검증. 고위험·고가치 산출물에서
  단일 self-correction보다 오류를 더 잘 잡음.
- **end-state 평가** — 상태를 여러 번 바꾸는 작업(파일 변경 등)은 매 단계가 아니라 **최종 상태**가
  맞는지로 평가. 복잡한 흐름은 "이 시점엔 이 상태여야 한다"는 체크포인트로 분할.
- **인간 검토** — 자동 평가가 놓치는 엣지케이스(드문 질의의 환각, 소스 선택 편향)를 잡음. 자동화가 있어도
  수동 테스트는 필수.
- **프로그램적 검증** — 객관적으로 확인 가능한 것(숫자 합, 형식, 링크 유효성)은 눈으로 보지 말고
  스크립트로 검사. 빠르고 재사용 가능.

## 검증 라운드 운영

1. 워커/PL이 결과 반환 → 평가자가 루브릭으로 채점.
2. pass면 종합 후보로 채택. fail이면 **무엇이 왜 부족한지**를 적어 해당 워커만 재실행
   (전체 재시작 금지).
3. 부족분이 새 정보가 필요한 종류면 PM이 추가 서브에이전트를 띄우거나 전략을 수정.
4. **반복 상한**(예: 2~3라운드)을 넘으면 현재 최선으로 마감하고 한계를 사용자에게 명시.

## 중단(Stop) 조건 — 폭주 방지

- **노력 예산** — 에이전트 수·도구 호출 상한을 사전 설정.
- **충분성 기준** — 완료 기준 충족 시 즉시 멈춤. "이미 충분한데 계속 도는 것"이 최대 낭비.
- **반복 상한** — 검증→재작업 라운드 횟수 제한.
- **수확 체감** — 새 에이전트가 의미 있는 신규 정보를 못 내면 종료.

## 실패 처리

- **체크포인트 & 재개** — 실패 지점부터 이어가도록 중간 상태 저장(처음부터 재시작 금지).
- **결정적 안전장치 + AI 적응** — 재시도 로직 위에, "도구 실패 중"을 에이전트에게 알려 스스로 우회.
- **관측 가능성** — 의사결정·상호작용 패턴을 추적해 근본 원인 진단.
- **컨텍스트 한계** — 한계 임박 시 완료분을 요약·외부 저장하고 깨끗한 새 서브에이전트로 핸드오프.
