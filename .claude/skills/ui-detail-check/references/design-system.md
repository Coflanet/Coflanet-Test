# 디자인 시스템

> Atomic Design, 디자인 토큰, Refactoring UI 원칙
> *컴포넌트와 시스템 단위*의 결정 기준.

---

## 1. Atomic Design (Brad Frost)

### 5단계 구조

| 단계 | 정의 | 예시 |
|---|---|---|
| **Atom** | 더 이상 쪼갤 수 없는 단위 | 버튼, 인풋, 라벨, 아이콘 |
| **Molecule** | 아톰들의 작은 결합 | 검색 폼 (인풋 + 버튼) |
| **Organism** | 분리 가능한 큰 단위 | 헤더, 카드 그룹, 폼 섹션 |
| **Template** | 페이지 구조 (콘텐츠 없음) | 와이어프레임 수준 |
| **Page** | 실제 콘텐츠가 들어간 화면 | 완성된 화면 |

---

### 활용 원칙

- Atom은 *단독으로 동작하지 않는다*. 항상 더 큰 단위 안에서 쓰인다.
- Molecule은 *재사용 가능한 가장 작은 단위*. 디자인 시스템의 핵심 단위다.
- Organism은 *맥락이 있다*. 예: 검색 결과 카드는 검색 페이지의 Organism.
- Template과 Page의 구분은 *콘텐츠 유무*. 작업할 때 헷갈린다면 같이 다뤄도 무방.

**왜**: 재사용 단위가 명확해지고, 컴포넌트 *조합*으로 화면을 만드는 사고가 정착된다.

## 2. 디자인 토큰

### 3계층 구조

**1. Primitive (원시 값)** — 실제 값
```
color-blue-500: #2563EB
spacing-4: 16px
font-size-3: 20px
```

**2. Semantic (의미 토큰)** — 역할 기반
```
color-action-primary: {color-blue-500}
spacing-component-padding: {spacing-4}
font-size-heading-3: {font-size-3}
```

**3. Component (컴포넌트 토큰)** — 특정 컴포넌트용
```
button-primary-background: {color-action-primary}
button-primary-padding: {spacing-component-padding}
```

---

### 왜 3계층이 필요한가

| 층 | 변경의 의미 |
|---|---|
| Primitive 변경 | 색상 자체를 바꿈 (예: 파랑 → 초록) |
| Semantic 변경 | 역할을 바꿈 (예: 주 액션 색을 다른 색으로) |
| Component 변경 | 특정 컴포넌트만 바꿈 (예: 버튼 패딩 조정) |

**핵심 효과**:
- 디자이너와 개발자가 *같은 언어*를 사용
- 다크 모드, 테마 전환이 *시맨틱 레벨*에서 가능
- "primary 컬러"를 바꾸면 모든 곳이 자동 반영

---

### 토큰 명명 규칙

**원칙**: `{category}-{property}-{variant}-{state}`

예시:
```
color-text-primary-default
color-text-primary-hover
color-background-surface-raised
spacing-padding-button-medium
```

> 이름이 길어 보여도, *역할이 명확*해야 시스템이 깨지지 않는다.

## 3. Refactoring UI 핵심 원칙

> 출처: Adam Wathan & Steve Schoger, *Refactoring UI*

### 색

- **회색이 가장 많이 쓰인다.** 9~10단계의 회색 스케일을 먼저 만든다.
- 채도가 높은 색은 *드물게*. 본문 옆 작은 강조 정도.
- "회색"이라고 채도 0의 무채색을 쓰지 말 것. 살짝 색조가 들어간 회색이 자연스럽다.

---

### 계층

- **위계는 *크기*가 아니라 *대비*로 만든다.**
- 같은 크기여도 색·두께로 차이를 낼 수 있다.
- 덜 중요한 것은 *없애는 것*이 아니라 *덜 보이게* 만든다.

```
중요한 것: 진한 색, 큰 크기, 굵게
덜 중요한 것: 흐린 색, 작은 크기, Regular
가장 덜 중요한 것: 더 흐린 색 (회색 스케일 활용)
```

---

### 그림자

- **작은 그림자**: 살짝 떠 있는 느낌 (드롭다운, 호버)
- **큰 그림자**: 공중에 떠 있는 느낌 (모달, 툴팁)
- **그림자 + 약간의 색조**: 완전 검정이 아닌, 살짝 색이 섞인 그림자가 자연스럽다
- **같은 페이지에서 그림자 깊이는 2~3단계로 제한**

---

### 여백

- 부족한 여백이 디자인을 *아마추어처럼* 보이게 한다.
- **의심스러우면 *더 늘려라*.**
- 타이트한 디자인은 *의도적*일 때만 작동한다.

---

### 디테일

- **보더**: 채도 낮은 회색. 검정에 가까울수록 *과해 보인다*.
- **둥근 모서리**: 컴포넌트마다 일관되게. **4 / 8 / 12 / 16px** 중 하나를 시스템으로 정함.
- **아이콘**: 라인 두께를 통일. 아이콘 세트 안에서 두께가 섞이면 어색하다.

## 4. 시스템 작업 시 결정 순서

새 컴포넌트나 화면을 시스템에 추가할 때:

1. **이미 있는 토큰으로 가능한가?** → 가능하면 그것을 사용
2. **새 Semantic 토큰이 필요한가?** → 역할이 새로 생겼다면 추가
3. **새 Primitive가 필요한가?** → 정말 새로운 값이 필요할 때만 (드물어야 함)
4. **컴포넌트 토큰을 정의하는가?** → 해당 컴포넌트에서만 쓰는 값일 때

> **시스템은 *늘리기*보다 *재사용*하는 방향으로 성장한다.**

## 5. 다크 모드 대응 원칙

### 핵심 규칙

- **단순히 색을 반전시키지 않는다.** 흰 배경 → 검은 배경이 아니다.
- 다크 모드는 *어두운 회색*에서 시작한다 (#121212 같은).
- 위계를 *더 밝은 회색*으로 만든다 (배경보다 살짝 밝은 카드).

---

### 색 매핑

| 라이트 모드 | 다크 모드 |
|---|---|
| 흰색 배경 (#FFFFFF) | 진한 회색 (#121212 ~ #1E1E1E) |
| 본문 텍스트 (Gray 900) | 본문 텍스트 (Gray 50 또는 100) |
| 보조 텍스트 (Gray 600) | 보조 텍스트 (Gray 400) |
| Primary 500 | Primary 400 (살짝 밝게) |

> 다크 모드에서는 *채도를 낮춘다*. 같은 채도의 색이 어두운 배경 위에서는 더 강하게 보인다.

---

### Elevation (계층 표현)

라이트 모드는 *그림자*로 계층을 표현한다.
다크 모드는 *밝기 차이*로 계층을 표현한다 (그림자가 안 보임).

```
레벨 0 (배경):   #121212
레벨 1 (카드):   #1E1E1E
레벨 2 (시트):   #232323
레벨 3 (모달):   #2C2C2C
```
